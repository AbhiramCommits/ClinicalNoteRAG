# Model Card: ClinicalNoteRAG

## Model details

**Name:** ClinicalNoteRAG (research prototype, version 0.1.0)

**System type:** A retrieval-augmented question-answering system, not a single
end-to-end trained model. The served system is composed of:

- **Corpus generator:** deterministic synthetic FHIR R4 generator
  (`clinicalnoterag.data.synthea_gen`) and templated note generator. All records
  are synthetic; no real patient data was used.
- **De-identifier:** regex/gazetteer fallback (`regex` backend) with typed
  reversible placeholders. Presidio is implemented and tried first but was not
  importable in this build.
- **Embedding model:** `sentence-transformers/all-MiniLM-L6-v2`, 384
  dimensions, L2-normalized. Offline fallback: deterministic hashed TF-IDF,
  512 dimensions.
- **Vector stores:** FAISS `IndexFlatIP` + SQLite sidecar (used for the full
  build and served API) and Postgres + pgvector behind the same interface
  (contract-tested against `pgvector/pgvector:pg16`).
- **Retriever:** dense + BM25 with reciprocal rank fusion, k=60; optional
  metadata prefilter.
- **Selected generator for `rag-tuned`:** deterministic `extractive-offline`
  generator plus a trained fallback MLP reranker.
- **LoRA adapter:** PEFT LoRA on `Qwen/Qwen2.5-0.5B-Instruct`, r=8,
  alpha=16, dropout=0.05, target modules `q_proj,v_proj`, trained with TRL
  SFTTrainer for 12 optimizer steps on CPU fp32, maximum length 1024, batch 1
  with gradient accumulation 4, learning rate 2e-4, seed 42. The adapter exists
  at `artifacts/adapters/clinical-lora/` and was evaluated as `rag-lora`; it was
  **not selected** because it did not learn the citation contract.
- **Fallback learned component:** 32-feature MLP reranker, hidden dimension
  32, 120 epochs, trained on 272 train pairs and 45 validation pairs, best
  validation loss 0.185113. It is stored at
  `artifacts/adapters/clinical-reranker/`.

**Training data provenance:** All SFT pairs and reranker candidates were derived
from the synthetic corpus and labeled benchmark generated by this repository.
No real patient data, scraped clinical text, or external PHI was used. The split
policy is strict patient-level disjointness: 24 train patients (162 items), 5
validation patients (30 items), 5 test patients (43 items). No patient appears
in more than one split. The split is recorded in `data/sft/split_manifest.json`
and produced by `clinicalnoterag.train.dataset.split_patients` with seed 42.

**Training path that ran:** LoRA status **trained** (341.539 s on CPU, validation
loss 2.162 → 2.025); fallback reranker status **trained** (held-out MRR
0.928571 → 1.000000, Recall@5 1.000). The primary `rag-tuned` deployment uses
the reranker; the LoRA adapter is reported separately and is never silently
substituted.

## Intended use and users

**Intended use:** Research on citation-grounded retrieval, abstention,
de-identification, synthetic clinical data engineering, evaluation with
confidence intervals, and PEFT benchmarking for healthcare TPO question
answering. Intended users are ML researchers, clinical informatics
researchers, and data engineers working with synthetic data in a governed
research environment.

**Out-of-scope use:** Diagnosis, treatment selection, triage, medication
recommendations, real claims adjudication, prior authorization, billing
decisions, patient-facing advice, or any production use with real PHI. The
system is not a medical device and has not been cleared or approved by any
regulator. Do not use it to make clinical, payment, or coverage decisions.

## Evaluation data

- Synthetic 300-patient FHIR corpus: 739 encounters, 1,104 conditions, 1,429
  procedures, 2,194 observations, 749 medication requests, 739 claims, 230
  denied claims.
- 235 QA items: 75 treatment, 60 payment, 60 operations, 40 adversarial.
- Gold answers, codes, supporting chunk ids and numeric values are derived from
  the same synthetic bundles that populate the index. The benchmark is
  closed-world: it is an upper-bound test of pipeline behavior, not a measure
  of real-world generalization.
- Held-out system comparison uses only patients assigned to the test split; no
  test patient was used to train the LoRA adapter or reranker.
- Tests and smoke used a separate committed 3-patient sample and generated
  20-patient corpus; the offline smoke achieved 5/5 checks.

## Ethical considerations

- **Synthetic-data caveat.** The notes are templated and easier than real
  clinical documentation. High scores do not transfer automatically to real
  records, coding distributions, or payer policies.
- **No clinician review.** Questions, answers, citations, and abstention
  decisions were not reviewed by clinicians. Citation support is a token and
  code check, not clinical entailment.
- **Automation bias.** A cited, confident-looking answer can still be
  incomplete (see the k=1 error analysis). Users must not treat citations as
  proof of clinical correctness.
- **Equity.** The synthetic name, condition, and payer tables are small and not
  representative. No fairness evaluation across demographics or languages was
  performed.
- **Payment harm.** Denial and appeal answers describe synthetic CARC reasons;
  they must not be used to draft real appeals or deny care.

## PHI and de-identification handling

- All PHI in notes is fake and injected by the generator (names, MRNs, SSNs,
  phones, emails, dates, addresses, ZIPs).
- De-identification produced typed placeholders and reversible maps. The maps
  are written to `artifacts/deid_maps/` outside the vector store, are
  PHI-bearing by design, and must be access-controlled and never committed or
  indexed. `artifacts/` is gitignored.
- The real build audited 1,478 documents and measured a PHI leak rate of 0.000
  with per-entity recall 1.000 for all eight entity types under the regex
  backend. Presidio was not importable, so this is **not** a real-world PHI
  guarantee. The audit is closed-world against the exact injected strings.
- The vector store contains de-identified text and metadata ids only; a test
  asserts that a sample patient's name and MRN do not appear in stored text or
  metadata.

## Bias and failure modes

- **Retrieval coverage:** fixed top-k can miss multi-fact evidence; k=1
  ablations show exact match dropping to 0.497 (dense), 0.405 (BM25), and 0.451
  (hybrid). Count and total questions can silently undercount.
- **Easy benchmark:** code-generated questions share vocabulary with fact
  chunks; performance is an upper bound.
- **Citation verifier:** token/code overlap can accept incomplete answers that
  quote one true fact while omitting others. It can also be conservative about
  valid paraphrases.
- **LoRA failure:** the 12-step 0.5B adapter produced 94.3% unsupported answers
  and no exact matches; small-scale tuning is not a substitute for evaluation.
- **De-identification:** regex gazetteer performance on unseen name formats,
  dialects, or address layouts is unknown.
- **Demographic bias:** no demographic fairness analysis was performed; the
  synthetic pools are not representative.

## Maintenance and refresh cadence

The Airflow-style DAG is designed for a daily refresh:
`generate_or_sync_corpus → deid_scan → chunk_and_embed → upsert → smoke_query →
publish_metrics`. The local runner executes the same functions. Any release
should re-run de-id audit, retrieval/eval ablations, the held-out system
comparison, tests/coverage, and the offline smoke path. Model or embedding
changes must update the backend name in artifacts and invalidate cached
embeddings/rerankers. The LoRA adapter should be retrained only on patient-
disjoint splits and must pass the citation and abstention checks before being
considered for `rag-tuned`.
